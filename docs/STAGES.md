# Vetro Look — этапы реализации Final Master Plan

Мастер-план (`VetroLook_Final_Master_Plan.md`) разбит на **9 этапов**. Каждый этап
оставляет приложение собранным, работающим и не ухудшает Image Mode: правило
§64 плана («Image Mode non-regression») действует на каждом шаге, а не в конце.

| Этап | Название | Содержание |
|---|---|---|
| 1 | Unified VetroLook | media routing, жизненный цикл режимов, Video Mode в общем окне |
| 2 | Playback Foundation | libmpv, D3D11 composition gate, `IPresentationTarget`, звук, базовый seek, дорожки, минимальный frame scheduler |
| 3 | Playback Quality | frame pacing, Resource Governor, capability matrix, бюджеты памяти и VRAM, батарея и температура |
| 4 | Navigation | timeline, preview engine, архитектура seek, покадровый шаг вперёд и назад |
| 5 | Subtitles | Vetro Bubble, morph и collapse, классификатор ASS, libass, PGS/VobSub |
| 6 | Product Completion + basic Streaming | resume, скорость, задержки, главы, очередь, скриншоты, A-B, SMTC, WASAPI, PiP, Direct URL/HLS/DASH → **V1** |
| 7 | Advanced Streaming | resolver, web-URL, живые потоки, reconnect |
| 8 | AI | Whisper, VAD, AI-субтитры, speech map, smart silence |
| 9 | Enhancement + Hardening | RTX Video, fallback улучшения, финальные бенчмарки, восстановление, release hardening → **V1.1** |

Прототипные гейты плана (§57) не выделены в отдельный этап: каждый выполняется
внутри своего этапа до того, как на его допущениях строится UI. Гейт B (mpv в
DirectComposition) — первое, что делается на этапе 2, потому что от него зависит
всё остальное в Video Mode.

## Этап 1 — Unified VetroLook (сделано)

Цель: фотография и видео становятся двумя режимами одного окна. Никакого второго
executable, никакой пересборки shell при смене типа файла.

Что появилось:

- **`src/media.h` / `media.cpp` — MediaRouter.** Дешёвая подсказка по расширению,
  затем ограниченная проба сигнатуры (4 КБ): ISO-BMFF с разбором brand'ов,
  Matroska/WebM, RIFF (AVI/WAVE/WebP, включая флаг ANIM), MPEG-TS/PS, FLV, ASF,
  Ogg, APNG, анимированный GIF и остальные. Здесь же живут канонические списки
  расширений; `Supported()` в `decoders.cpp` теперь обращается к ним, поэтому
  списки не могут разойтись. `MediaSignature()` даёт стабильный идентификатор
  файла для пофайлового состояния будущих этапов.
- **`src/modes.h` / `modes.cpp` — жизненный цикл режимов.** Состояния из
  Appendix B, счётчик media generation и `ModeCaps` из Appendix A.2. Машина
  чистая: она не знает ни про Direct2D, ни про декодер, и говорит shell'у, что
  именно нужно освободить при уходе из режима.
- **`src/shellmedia.h` / `.cpp`.** Длительность, размер кадра, частота кадров и
  кодеки из property handler'а Windows; постер-кадр из кэша миниатюр шелла.
  Ни одной видео-подсистемы в процессе.
- **`src/videomode.h` / `.cpp` — Video Mode.** Собственный worker с политикой
  latest-wins и generation-токенами, поверхность с постер-кадром и стеклянной
  подписью в языке Vetro. Playback engine второго этапа встаёт на это место, не
  трогая shell.
- **Навигация.** Список соседей обходит медиа, а не только фотографии, поэтому
  filmstrip в смешанной папке идёт фото → видео → фото. Плитки видео берут
  постер из шелла.
- **Ошибочные расширения.** Окно классифицирует по имени — на потоке, который
  обязан быть быстрым. Пробу делает тот worker, который уже открыл файл, и файл
  переоткрывается один раз в том режиме, который назвали байты. `.jpg` с MP4
  внутри открывается, `.mp4` с фотографией внутри — тоже.
- **Возможности вместо `if(video)`.** Zoom, crop, rotate, fit и Edit отсутствуют
  в Video Mode, а не «есть, но ничего не делают»: Layout строит док из
  `ModeCaps`, PaintDock рисует ровно то, что Layout разместил.

Тесты: `VetroMediaTests` — 62 проверки против синтетических заголовков
контейнеров и переходов машины режимов. Навигация Image Mode после изменений:
p50 5.52 мс, 0 переходов дольше 16 мс — в пределах прежней базы 5.56–5.58 мс.

Что сознательно **не** сделано на этапе 1: воспроизведения нет. Video Mode
показывает первый кадр и факты о файле. Никаких кнопок play, которые ничего не
делают, в интерфейсе тоже нет.

### Границы, оставленные следующим этапам

- Библиотека и индекс по-прежнему только фотографические (`Supported()`);
  фильмы видны в папочной навигации и filmstrip'е, но не в timeline библиотеки.
- Explorer-preview (`Space`) остаётся фотографическим.
- Удаление, Save, Print для видео выключены (строки меню гаснут сами, потому что
  кадра нет), полноценные действия появятся вместе с движком.

## Этап 2 — Playback Foundation (сделано)

Цель: в том же окне и в том же режиме появляется настоящее воспроизведение.

### Гейт композиции (Prototype B) — пройден

`tests/mpv-composition-probe.cpp`, цель `VetroMpvProbe`. Проверяет ровно тот
libmpv, который лежит рядом с приложением, и отвечает на вопрос, на котором
строится весь Video Mode: можно ли отдать вывод mpv в наше дерево
DirectComposition. Результат на pinned-сборке (client API 2.5):

| Проверка | Результат |
|---|---|
| `vo=gpu-next`, `gpu-context=d3d11`, `d3d11-output-mode=composition` | приняты |
| `display-swapchain` читается как указатель | да, **64 мс** от старта процесса |
| swapchain windowless (`OutputWindow == nullptr`) | да, 3 буфера |
| принят как content нашего визуала в окне без redirection surface | да |
| resize через `d3d11-composition-size` | тот же объект, буферы следуют размеру |
| pause / exact seek / resume | 5.00 с, ~600 мс до устойчивого кадра |
| аппаратный декод | `d3d11va` |
| dropped frames за resize и seek | 0 |

Один результат отрицательный и записан как ограничение: в composition-режиме у
mpv нет HWND, поэтому он не знает, на какой дисплей попадает картинка, и не
сообщает target colour space. Для SDR это ничего не меняет; HDR-вывод потребует
передавать цветовое пространство дисплея со стороны Vetro Look — это цветовая
работа этапа 3, а не дефект пути.

### Что уже сделано

- **Presentation seam.** Дерево композиции стало двухслойным: видео снизу,
  интерфейс со своей альфой сверху, клип с радиусом окна. Ни один тип движка не
  пересекает границу — `GfxSetVideoContent(IUnknown*)` и всё.
- **`src/playback.h` — `IPlaybackEngine`.** Позиции, длительности, команды,
  снимок состояния, дорожки. Ни одного mpv-типа в заголовке.
- **`src/mpvengine.cpp`.** Единственный файл, знающий про mpv. Библиотека
  грузится по имени при первом открытии видео: фотография не платит за
  видеостек (рабочий набор сессии с одними фотографиями не изменился), а машина
  без библиотеки остаётся рабочим просмотрщиком изображений и честно об этом
  сообщает. Свойства не опрашиваются, а наблюдаются; wakeup движка приходит
  сообщением в окно.
- **Управление.** Space — play/pause, `←/→` — seek на 10 с, `Ctrl+←/→` —
  соседний файл, клик и перетаскивание по таймлайну. Во время перетаскивания —
  дешёвый seek не чаще чем раз в 80 мс, точный — на отпускании.
- **Транспорт.** Стеклянная панель в языке Vetro: play/pause, прошло, дорожка,
  длительность. Пока воспроизводить нечего — на том же месте остаётся подпись с
  фактами о файле, поэтому поверхность не перестраивается при старте.
- **Дорожки.** `Tracks()` / `SelectTrack()` реализованы в движке; UI выбора
  дорожек появится вместе с меню «ещё» на этапе 6.

### Ограничения, честно записанные

- Планировщик кадров пока собственный у mpv (`video-sync=audio`). Своего
  Presentation Scheduler и телеметрии present-времени нет — это этап 3.
- HDR не настроен (см. гейт выше), fullscreen, PiP, скриншоты, resume — дальше
  по этапам.
- Библиотека и Explorer-preview остаются фотографическими, как и на этапе 1.


### Форма окна, стекло и дизайн-система

- **Окно принимает форму фильма.** 16:9 даёт окно 16:9, вертикальная съёмка —
  вертикальное окно. Форма берётся из первого же сообщения движка о размере
  кадра, удерживается при перетаскивании края (`WM_SIZING`) и снимается при
  выходе из режима. Минимальный размер окна в Video Mode меньше обычного: иначе
  вертикальное видео не поместилось бы в окно, обязанное быть шире 760.
- **Матовое стекло над фильмом.** Direct2D не может прочитать кадр — картинку
  рисует движок в свой swapchain. Поэтому размытие делает компоновщик: на каждую
  стеклянную панель создаётся визуал с тем же swapchain, к нему применяется
  `IDCompositionGaussianBlurEffect`, и он обрезается по скруглённому
  прямоугольнику панели. Панели живут между фильмом и слоем интерфейса; сам
  интерфейс рисует поверх только тон, кромку и содержимое. Там, где фильтр-эффекты
  недоступны, панель остаётся более плотной заливкой — слабее, но не сломано.
  Пока chrome скрыт, стекла нет вовсе: размытие — самое дорогое, что есть на
  экране, и просмотр фильма за него не платит (+9 % одного ядра только когда
  панели видны).
- **Дизайн взят из установленных скиллов** `apple-hig-designer` и
  `apple-design-toolkit` (`.claude/skills/`): шкала шрифтов и радиусов, capsule и
  концентрические скругления, цели нажатия не меньше 44 pt, обратная связь
  масштабом 0.96 вместо вспышки, многослойная заливка стекла (плотность → подсветка
  → specular-кромка) и мягкая тень r15/y8. Из пакета `apple-design-toolkit`
  установлен только `figma-apple-kit-extract` вместе с его README: остальные три
  скилла пакета — сборка macOS-приложений, обход политики инструментов и
  беспарольный root-агент — к Windows-приложению отношения не имеют, а последний
  и вовсе про привилегированное выполнение.

### Лестницы и измерения

- **Render ladder (§8.2).** Движок поднимается по списку `gpu-next` → `gpu`;
  обе ступени выводят через ту же composition-поверхность, поэтому shell не
  замечает разницы. Выбранная ступень попадает в снимок состояния.
- **Decode ladder (§8.1).** `hwdec=auto-safe`: аппаратные пути, известные как
  безопасные на этой машине, затем программный. Ступень видна как `hwdec-current`.
- **Аудиоустройства.** Движок отдаёт список устройств и принимает выбор;
  пустой идентификатор означает системное по умолчанию — туда же система
  возвращается, когда выбранное исчезает. Политика hot-plug целиком — этап 6.
- **Телеметрия.** При `VETRO_DEBUG=1` сессия пишет `%TEMP%etro-session.log`, и
  раз в пять секунд туда уходит строка вида:

```text
PLAYBACK renderer=gpu-next hwdec=d3d11va fps=24.00 dropped=0 late=0 avsync=0.000 pos=14.8
```

  Это то, к чему этап 3 будет прикладывать собственный Presentation Scheduler.
  Измерено на серии 1080p: 24.00 fps, ноль пропущенных и ноль поздних кадров,
  A/V-рассинхрон 0.000 с.
- **Стоимость интерфейса.** Проигрывание 1080p — около 47 % одного ядра со
  скрытым chrome; видимое стекло добавляет примерно 9 %. Перерисовка окна
  происходит только когда на экране что-то изменилось, а не на каждое событие
  движка.

## Этап 3 — Playback Quality (сделано)

Цель: кадр не просто декодируется быстро, а показывается вовремя — и всё
остальное в приложении уступает ему дорогу само, без вмешательства человека.

Три новых модуля, и все три решают чистыми функциями от структуры, поэтому их
можно проверить на машине, которой у пользователя нет:

- **`src/capability.h` / `capability.cpp` — матрица возможностей (§13).**
  Адаптер и его объём памяти, профили аппаратного декода (спрошены у Direct3D, а
  не у движка: ответ нужен раньше, чем появляется движок), точная частота
  обновления, состояние HDR и уровень белого SDR из конфигурации дисплея, пиковая
  яркость панели из DXGI, RAM, бюджет VRAM, питание и потолок частоты. Отдельно
  «что машина есть» (опрашивается один раз) и «что машина делает сейчас»
  (дёшево и часто).
- **`src/pacing.h` / `pacing.cpp` — frame pacing (§11).** Решение о том, по
  какому таймеру показывать кадры, плюс измерение стоимости наших собственных
  кадров интерфейса.
- **`src/governor.h` / `governor.cpp` — Resource Governor (§12, Appendix F).**
  Давление, лестница деградации, гистерезис, политика питания.

### Frame pacing

В composition-режиме у движка нет окна, поэтому он не знает ни частоты
обновления, ни того, на какой дисплей попадает картинка. Теперь знает: частоту
даём мы (`display-fps-override`), и вместе с ней — режим синхронизации.

| Условие | Решение |
|---|---|
| частота дисплея кратна частоте фильма (24 в 120) | по дисплею, интерполяция не нужна |
| неровная кратность (24 в 60, 23.976 в 180) | по дисплею; интерполяция — только по явному выбору «Плавность» |
| дисплей медленнее фильма (60 в 50) | по дисплею с плановым отбрасыванием |
| частота фильма или дисплея неизвестна | по аудиочасам |
| поздние кадры, батарея, throttling, программный декод | по аудиочасам |
| «Низкая задержка» | по аудиочасам |

Явный выбор «Плавность» уступает только в аварийном режиме губернатора (§F.4):
предпочтение пользователя — не разрешение ронять кадры бесконечно.

У самого плана тоже есть выдержка, и по более резкой причине, чем у губернатора:
переход на синхронизацию по дисплею сам по себе даёт один-два поздних кадра,
поздний кадр — довод в пользу аудиочасов, а аудиочасы этот кадр убирают. Без
паузы в три секунды между сменами плана этот цикл крутится со скоростью опроса.
Выбор пользователя, смена дисплея и первое появление частоты фильма выдержку не
ждут — последнее не смена решения, а первое решение для этого фильма.

Кадры интерфейса измеряются отдельно от фильма: от первой отрисовки до момента
готовности к Present, без ожидания вертикальной синхронизации — ждать не значит
работать (Appendix F.3). Судятся они по 60 Гц, а не по частоте панели: фильм
показывает движок на своём слое, и дисплей на 180 Гц не делает наш chrome
опоздавшим. Окно измерений очищается после создания окна, изменения размера,
смены дисплея и открытия нового фильма — кадры, дорогие по понятным причинам, не
должны ничего решать.

### Resource Governor

Губернатор отвечает не «загружен ли GPU», а «успеет ли следующий обязательный
кадр и что можно урезать». Сигналы: остаток бюджета кадра, поздние и
отброшенные кадры (отдельно декодером и отдельно выводом), A/V-дрейф, давление
RAM и VRAM, батарея, режим энергосбережения, потолок частоты, скрытое окно.
Побеждает худший сигнал — губернатор, который усредняет входы, игнорирует
именно то, что сломалось.

Лестница (§12.4) выражена четырьмя уровнями Appendix F.2, и сегодня к ней
подключено то, что уже существует:

| Уровень | Что разрешено |
|---|---|
| Headroom | всё |
| Balanced | превью мельче и ленивее, анализ сцен выключен |
| Constrained | префетч соседних фото и индексация библиотеки остановлены, размытие упрощено, фоновая работа не начинается |
| Emergency | только воспроизведение: стекла нет |

Гистерезис: деградация после 1.2 с устойчивого давления (0.4 с, если давление
уже тяжёлое), возврат — после 5 с устойчивого запаса, не чаще одного шага в 2 с,
и всегда на один уровень. Между порогами 0.25 и 0.60 не происходит ничего —
этот зазор и есть защита от «RTX ON → OFF → ON».

Разрешения читают те, кто делает работу: `Frame()` — про стекло и радиус
размытия, декодирующий worker — про префетч соседей, `IndexSetPaused()` —
про обход библиотеки. Превью, Whisper и RTX спросят на своих этапах.

### Бюджеты памяти и VRAM

Очереди движка больше не остаются на значениях по умолчанию: объём чтения
вперёд считается от свободной памяти машины (одна тридцать вторая, не меньше
32 МБ и не больше 512 МБ), назад — четверть от этого, и вдвое меньше обоих,
когда губернатор ниже Balanced. VRAM читается как бюджет процесса у DXGI, а не
как «занято на карте»: бюджет уже учитывает остальные приложения, поэтому
приближение к нему означает вытеснение.

### Батарея и температура

Windows не даёт обычному процессу читать температуру, поэтому термическое
состояние выводится из честного косвенного признака — потолка частоты
процессора относительно его максимума; устойчивое падение ниже 80 % считается
защитой машины от самой себя. На батарее выключается улучшение и анализ сцен,
интерполяция не включается никогда, а скрытое окно на батарее останавливает и
индексацию. Режим энергосбережения вдобавок держит потолок уровня на Balanced.

### Цвет

Дисплей описывается движку на его языке: HDR-панель получает десятибитный
PQ-вывод (`d3d11-output-csp=pq`, `target-prim=bt.2020`, `target-trc=pq`) и
пиковую яркость самой панели. Ограничение записано честно: цветовой конвейер
выбирается в момент создания вывода, и в composition-режиме пересоздать его на
лету нельзя — смена дисплея на HDR помечается в снимке (`targetPending`) и
вступает в силу со следующим фильмом. На этой машине HDR проверить нечем:
дисплей SDR, 180 Гц.

Заявленный EDID широкий охват намеренно **не** используется как повод
перекрашивать: пока Windows не управляет цветом, на панель уходят sRGB-числа, и
отображение по P3 на основании одной лишь надписи в EDID обесцветило бы каждый
фильм. Охват берётся из конфигурации дисплея, а заявление панели остаётся в
диагностике.

### Настройки и диагностика

В меню, пока открыт фильм, появились три строки: **Синхронизация**
(Авто / Плавность / Задержка), **Питание** (Авто / Производительность /
Экономия) — обе переживают сессию, — и **Диагностика**, которая кладёт в буфер
обмена очищенный блок §53: адаптер, профили декода, дисплей, память, питание,
уровень губернатора, план синхронизации, стоимость кадров интерфейса, движок,
конвейер и счётчики кадров. Ни путей, ни имён файлов, ни имени пользователя.

### Измерения

Серия 1080p H.264 на дисплее 180 Гц, аппаратный декод `d3d11va`, рендер
`gpu-next`:

| Величина | Значение |

| Кадров в секунду | 24.00 |
| Пропущено кадров выводом / декодером | 0 / 0 |
| Поздних кадров | 0 |
| A/V-рассинхрон | 0.000 с |
| Дрожание интервала | 0.0002 |
| Кадры интерфейса, p95 | 1.9 мс из 16.67 |
| Уровень губернатора | Headroom, ни одного переключения |

Строка телеметрии теперь выглядит так:

```text

 decdrop=0 late=0 avsync=0.000 jitter=0.0002 tier=3 margin=14.7 ui_p95=1.9 pos=15.0
```

Image Mode не пострадал: p50 навигации 5.58 мс (последовательная 5.88 мс), ни
одного перехода дольше 16 мс из 414, пиковый рабочий набор 90 МБ — прежняя база.

Тесты: `VetroQualityTests` — 69 проверок. Таблица решений pacing целиком,
перцентили кадров, веса давления, порядок лестницы, гистерезис (включая

оба примера выбора конвейера из §13.2. Последняя секция опрашивает эту машину и

### Ограничения, оставленные дальше

## Этап 4 — Navigation (сделано)

Цель: по таймлайну видно, куда идёшь, ещё до того как отпустишь кнопку, и кадр
можно разобрать по одному.

### Гейт превью — пройден

`tests/preview-probe.cpp`, цель `VetroPreviewProbe`. Вопрос тот же по форме, что
и на этапе 2: можно ли получать произвольные кадры вторым, безоконным декодером,
не трогая тот, который играет. Ответ на серии 1080p H.264:

| Проверка | Результат |
|---|---|
| `vo=null` + `screenshot-raw video` | кадры возвращаются |
| первый кадр, включая запуск декодера | **54 мс** |
| произвольный seek по фильму | 10–32 мс, среднее 26 мс |
| кадр приходит уже уменьшенным (`vf=scale`) | 241×136 |
| повторный запрос той же позиции | 0 мс, из кэша |
| движок воспроизведения при этом | не участвует вовсе |

### Preview Engine

`src/preview.h` / `preview.cpp`. Отдельный декодер: без звука, без субтитров,
без вывода и **без аппаратного декодера** — тот принадлежит фильму, и превью,
которое его забирает, стоит кадров (§12.3). Три правила держат всю конструкцию:

- **Позиции квантуются.** Указатель порождает сотни различных меток времени в
  секунду, и каждая из них стала бы ключом кэша (H.1). Шаг зависит от
  длительности: около двухсот корзин на любой фильм, поэтому девяностосекундный
  ролик и шестичасовая запись не получают одинаковую плотность (§19.6).
- **Побеждает последний.** Кадр для позиции, которую указатель уже покинул,
  выбрасывается, а не рисуется (§19.3).
- **Запросы сливаются.** Указатель быстрее любого декодера, поэтому запросы не
  становятся в очередь: декодируется тот, на котором указатель остановился
  (§19.4).

Прогрессивный показ (§19.5): пока точный кадр декодируется, показывается соседняя
корзина — она правдива относительно того, где вы примерно находитесь, — и
заменяется на месте. Дальше двух корзин не показывается ничего: кадр из другой
сцены был бы уже ложью. Кэш L1/L2 ограничен байтами, а не числом кадров: кадр из
4K-фильма в девять раз больше кадра из 720p, а счётчик бюджетировал бы их
одинаково. Губернатор управляет размером кадра, паузой слияния и самим
разрешением декодировать (§12.4, шаги 1–2); из кэша кадры показываются и тогда,
когда новое декодирование запрещено.

Карточка превью живёт над транспортом и сделана из того же матового материала —
это тот же объект, отвечающий на вопрос, а не отдельное окно. Когда кадра нет и
быть не может, карточка показывает только отметку времени: честное «здесь, но
показать нечем» лучше выдуманного кадра (§18.2).

### Seek

Каждая фиксация получает номер поколения (§20.2): работа, начатая для прежней
позиции, не имеет права вернуться как текущая. Порядок при фиксации ровно такой,
как в §20.3 — сначала поколение, потом движок, — поэтому то, что уже в полёте,
становится устаревшим до того, как движок тронут. Во время перетаскивания seek
дешёвый и не чаще раза в 80 мс; на отпускании — точный, потому что это и есть тот
единственный кадр, на который посмотрят.

Шаг стрелок — настройка (§20.4): 5 или 10 секунд, по умолчанию 10, живёт между
сессиями.

### Покадровый шаг

`,` и `.` — кадр назад и вперёд, и то же самое на Shift со стрелками. Фильм
ставится на паузу сам: продолжающий идти фильм под покадровым шагом — это не шаг.
Шаг идёт по реальному порядку представления, поэтому он верен и для переменной
частоты кадров (§21.5). Проверено на серии 24 fps: 24 шага назад — ровно −1.0 с.
Ограничение истории кадров (§21.4) — это тот же бюджет `demuxer-max-back-bytes`,
который этап 3 уже считает от свободной памяти машины.

Image Mode после этапа: p50 навигации 5.42–5.72 мс, ни одного перехода дольше
16 мс из 414, пиковый рабочий набор 91 МБ.

### Оставлено дальше

- L3, дисковый кэш превью (§19.7), не сделан: ему нужен склад, ключом которому
  служит сигнатура медиа, — ровно тот же, что понадобится resume на этапе 6.
  Строить его дважды не нужно.
- Zoom таймлайна и адаптивная плотность по зуму (§19.6) появятся вместе с самим
  зумом таймлайна.

## Этап 5 — Subtitles (сделано)

Цель: реплики выглядят как часть Vetro Look, а авторская вёрстка остаётся
авторской.

### Классификатор

`src/subtitles.h` / `subtitles.cpp`. Решение принимается **на реплику, а не на
файл** (§23.2), потому что один ASS-трек сплошь и рядом несёт и диалог, и
надписи:

| Что в реплике | Кто рисует |
|---|---|
| простой текст, курсив, цвет, `\an1`–`\an3` | Vetro Bubble — просмотрщик |
| `\pos`, `\move`, `\clip`, `\t`, `\fad`, поворот, караоке, `\p1` (вектор) | движок, libass, нетронутой |
| `\an4`–`\an9` — привязка к месту кадра | движок |
| PGS, VobSub, DVB | движок: у картинки нет текста, который можно переверстать (§26.2) |

Проверено на реальном ASS рядом с серией: в 0:05 диагностика говорит
`dialogue, drawn by the viewer (ass)` и показывает текст реплики, в 0:13 —
`authored typesetting, drawn by the engine (ass)`, и надпись с `\pos` и
поворотом выходит ровно там, где её поставил автор, в своём стиле. В 0:22 —
снова диалог: `{\i1}` — это оформление, а не постановка.

Внешние субтитры подбираются так, как ожидает человек: `movie.srt`,
`movie.ru.srt`, `movie.ass`, папки `subs/` и `subtitles/` (§22.3). Поиск идёт
при загрузке и первый кадр не задерживает.

### Vetro Bubble

Матовое стекло того же материала, что и транспорт, форма — по тексту, а не по
фиксированной плашке (§24.2): ширина и высота меряются по реальной раскладке с
переносами, максимум 74 % ширины кадра. Никаких чёрных прямоугольников, и
типографика важнее эффекта. Размытие — локальное: под пузырь подставляется тот
же приём, что и под панели, то есть компоновщик размывает **только** его область,
а не кадр 4K ради маленькой плашки (§24.3).

Пузырь — физический объект (§25):

- между репликами он **не мигает**: форма удерживается и перетекает в новую;
- после настоящей тишины (по умолчанию 3 с, §25.7) он схлопывается в точку и
  исчезает уже оттуда, а не гаснет на месте;
- реплика, пришедшая во время схлопывания, **отменяет** его и перенацеливает ту
  же геометрию, а не встаёт в очередь за второй анимацией (§25.5);
- текст уходит раньше формы — чтобы он оставался читаемым, пока ещё крупный;
- **анимация никогда не отнимает время чтения** (§25.6): текст верстается в той
  форме, к которой пузырь идёт, а не в той, которую стекло успело принять.

Reduce Motion — это не «медленнее», а «без анимации вовсе» (§24.4); при нехватке
ресурсов губернатор снимает размытие, оставляя более плотный материал.

Субтитры — не chrome: когда панель управления уходит, пузырь остаётся и
опускается на своё место. Это единственный элемент интерфейса, который рисуется
и при полностью скрытом chrome, и ради него в этом случае включается ровно одна
стеклянная поверхность.

Тесты: 25 проверок в `VetroQualityTests` — таблица классификатора целиком,
разбор ASS в чистый текст, и весь автомат пузыря: удержание в паузе диалога,
схлопывание после тишины, спасение схлопывания новой репликой, уход текста
раньше формы, Reduce Motion.

### Оставлено дальше

- PGS/VobSub идут по тому же пути, что и сложный ASS, — их рисует движок; на
  этой машине не на чем проверить, образца нет.
- Смещение субтитров, размер и выбор дорожки «на файл» — этап 6, вместе с
  хранилищем состояния по сигнатуре медиа.
- AI-субтитры Whisper — этап 8, как и было записано.

## Этап 6 — Product Completion + basic Streaming (сделано) → **V1**

Цель: то, из-за отсутствия чего плеером не пользуются, даже если воспроизведение
безупречно.

### Что фильм о себе помнит

`src/mediastate.h` / `mediastate.cpp`. Ключ — сигнатура медиа из `media.h` (путь,
размер, время записи), поэтому переименованный файл остаётся тем же фильмом, а
другой файл по тому же пути — не тем же. Хранится позиция, выбранные дорожки и
смещения звука и субтитров; записей не больше шестисот, вытесняются давние,
файл пишется раз в пять секунд и ещё раз при закрытии, через временный файл с
переименованием — прерванная запись не оставляет половину склада.

**Resume** предлагается не всегда: первые полминуты и последние полминуты не
предлагаются, как и всё после 98 % длительности. Фильм, доведённый до титров, —
это фильм, который начинают заново. Возврат объявляется тостом: фильм, молча
начавшийся с середины, читается как ошибка.

### Управление во время просмотра

| Действие | Клавиша |
|---|---|
| Кадр вперёд / назад | `.` и `,`, либо Shift со стрелками |
| Глава вперёд / назад | PageDown / PageUp |
| Смещение субтитров | `Z` и Shift+`Z` |
| Смещение звука | `X` и Shift+`X` |
| Кадр в файл | `S` |
| Отрезок A-B | `L` (начало → конец → выключить) |
| Картинка в картинке | `P` |
| Открыть адрес из буфера | Ctrl+V |

Скриншот пишется в «Изображения / Vetro Look» и называется по фильму и позиции в
нём, а не по часам на стене: два кадра из одной сцены оказываются рядом. Когда
субтитры рисует движок, они — часть картинки и попадают в кадр; когда их рисует
просмотрщик, снимок остаётся снимком фильма.

Смещения и выбор дорожки принадлежат фильму и возвращаются вместе с ним.

### Очередь

Досмотренный фильм уступает место следующему в той же папке, в том же порядке,
в каком их показывает filmstrip. Один раз на окончание, и не тогда, когда
включён повтор отрезка.

### Картинка в картинке

То же окно, маленькое и поверх всех: не второе окно и не второй декодер — фильм
уже скомпонован здесь, и копия стоила бы второго декодирования. Внутри остаётся
только фильм и его транспорт; папка, заголовок, док и кнопки окна — это про
окно, в котором работают, а это окно — то, на которое поглядывают.

### Системные элементы управления

`src/smtc.cpp`, на ABI-заголовках, без языковой проекции ради четырёх
интерфейсов. Windows видит Vetro Look как источник: название фильма, папка,
статус, и своя шкала времени. Проверено запросом к
`GlobalSystemMediaTransportControlsSessionManager`:

```text
VetroLook.exe | Playing | title='<film>.mkv' | folder='<folder>' | pos=00:06:36 of 01:01:32
```

Кнопки работают в обе стороны: `TryPauseAsync` из системы ставит фильм на паузу,
`TryPlayAsync` возвращает к воспроизведению — то есть клавиша воспроизведения на
клавиатуре и панель на экране блокировки управляют именно этим окном.

### Звук

Вывод назван явно — WASAPI, — чтобы машина, которая иначе выбрала бы что-то своё,
звучала как все остальные. Эксклюзивный режим доступен, но **без строки в меню**:
он выключает звук у всего остального на машине, а переключатель с таким эффектом
следует искать, а не находить случайно. `AudioExclusive=1` в ключе настроек.

### Потоки

`Direct URL`, HLS и DASH открываются по адресу: аргументом командной строки или
Ctrl+V из буфера. У адреса нет папки, соседей, миниатюры и места в библиотеке,
поэтому у него свой путь через `Open`, а не ветка внутри файлового.

Проверено на живом HLS (`test-streams.mux.dev`, 10:35, 60 fps): манифест
разобран, поток играет, длительность и таймлайн на месте.

При `VETRO_DEBUG=1` предупреждения самого движка попадают в сессионный лог —
разница между «loading failed» и знанием, какой хост, какой сертификат или какой
кодек (Appendix G). Первая же попытка этого потока показала и известное
ограничение composition-режима своими словами:
`vo/gpu-next/d3d11: Failed to query swap chain's output information`.

### Измерения

Image Mode после этапа: p50 навигации 5.57–5.73 мс, ни одного перехода дольше
16 мс из 414, пиковый рабочий набор 96 МБ. Воспроизведение 1080p: 24.00 fps,
ноль пропущенных, ноль поздних, A/V 0.001 с.

Тесты: `VetroQualityTests` — 97 проверок, включая правило resume целиком.

### Оставлено дальше

- Разрешение ссылок на страницы (YouTube и подобное), живые потоки с DVR-окном и
  reconnect с backoff — этап 7, как и было записано.
- Дисковый кэш превью (L3) теперь имеет, где жить: склад по сигнатуре медиа
  построен, и кэш ляжет рядом с ним.
- Главы показываются тостом по клавише; меток на таймлайне нет — таймлайн
  принадлежит текущему дизайну плеера, и врезаться в него ради этого не стоило.

## Этап 7 — Advanced Streaming (сделано)

Цель: адрес любого вида открывается тем путём, который ему подходит, живой поток
не притворяется фильмом, а оборвавшаяся связь восстанавливается сама.

### Какой это адрес

`src/streaming.h` / `streaming.cpp` — чистый словарь без движка и сети, поэтому
каждое правило проверено на строках, а не на сервере, который сегодня отвечает.
`ClassifyAddress` различает прямую ссылку, HLS, DASH, страницу и сервис, который
отдаёт только DRM (66.9):

- прямая ссылка и манифест открываются сразу;
- страница уходит в resolver;
- DRM-сервис (Netflix, Disney+, Кинопоиск, Okko, ivi и подобные) получает
  предложение сразу — без попытки и без цикла повторов (66.10). Хост сравнивается
  по границе точки: `notnetflix.com` — обычная страница.

### Resolver

`src/resolver.h` / `resolver.cpp`. Отдельный процесс, не часть пути
воспроизведения (9.5, Appendix T):

- реализация — yt-dlp, **которого приносит пользователь**: какие сайты он читает,
  меняется каждую неделю, и это не обещание Vetro Look. Ищется в `resolver\`
  рядом с программой, затем в `%LOCALAPPDATA%\VetroLook\resolver\`, затем в PATH;
- получает один адрес одним аргументом после `--`, без конфигурации, без cookies,
  без плейлиста; адрес с кавычкой, пробелом или не-http схемой не передаётся;
- job object: память до 1 ГБ, не больше шести процессов, убивается вместе с
  окном; таймаут 45 с; новый запрос отменяет старый;
- дочернему процессу выставлен UTF-8, поэтому кириллический заголовок страницы
  доходит кириллицей и называет окно;
- сайт, разделивший картинку и звук, играет обоими адресами; `User-Agent` и
  `Referer` передаются движку, остальные заголовки — нет.

Проверено заглушкой с тем же контрактом вывода (`VetroResolverStub`, собирается
как `yt-dlp.exe`): страница разрешается за 0.1 с и играет, заголовок
«Страница с фильмом» в окне; DRM-ответ даёт предложение; зависший помощник убит
через 45.1 с, окно всё это время отвечало, процессов не осталось.

### Живой поток

Живой поток не притворяется фильмом (G.1). Выяснилось на настоящем потоке: для
живого HLS движок сообщает **длину, которая растёт вместе с краем** (616 → 622 с),
а окно начинается не с нуля (595 с). Поэтому признак — «длины нет *или* она
растёт», а таймлайн показывает окно, накопленное с момента подключения:

- справа вместо длины — `● LIVE` (в том же шрифте и цвете, что и длина);
- позиция и перемотка считаются от начала окна, а не от часов потока;
- `End` — к прямому эфиру; превью и отрезок A-B для живого потока выключены.

Проверено на `demo.unified-streaming.com`: окно 595.2 → 618.2 с, `End` перевёл
позицию с 612.0 на край 618.2.

### Переподключение

Два уровня. Внутри одной загрузки движок сам повторяет запрос. Если он сдался,
Video Mode открывает поток заново с backoff 1, 2, 4, 8, 16 с, дальше каждые 30 с —
восемь попыток для потока, который уже играл, и две для того, который не играл ни
разу: опечатка в адресе — не авария сети.

Самое дорогое открытие этапа: этот libmpv читает HTTP через **curl**, и когда
связь пропадает, он не сообщает ни ошибки, ни конца файла — он ставит позицию на
длину фильма. Поэтому, кроме ошибки и «кончился раньше длины», есть третий
признак — сторож: последняя строка движка — окончательный отказ сети
(«transfer failed», не «retrying»), в буфере ничего, и фильм с тех пор не
продвинулся. Позиция для возврата берётся в момент отказа, а не после, иначе
возврат шёл в конец фильма. Сторож тикает на собственном таймере окна: зависший
поток не рисует кадров и не будит цикл отрисовки.

Проверено сценарием с локальным HTTP-сервером (Range) и настоящим фильмом на
3140 МБ: сервер остановлен на 20.5 с → «Поток прервался. Переподключаюсь…» →
попытки через 1, 2, 4, 8 с → сервер поднят → поток открыт на 20.5 с, доиграл до
52.5 с с 10 с в буфере, «Поток восстановлен».

### Почему не играет — одним предложением

404/410 — «Этого адреса больше нет», 401/403 — «Сервер не пускает», проверка
сертификата — отдельное предложение (TLS никогда не игнорируется молча), вход в
аккаунт, DRM, «на странице не нашлось открытого потока». Слова движка остаются в
Diagnostics: там же тип источника, окно, запас в буфере, состояние сторожа,
число переподключений и последние строки движка.

### Попутно исправлено

Журнал сессии (`std::wofstream` без локали) замолкал навсегда на первом символе
не из ASCII. Первой такой строкой оказалось русское «Переподключаюсь…», поэтому
несколько прогонов выглядели как зависание. Теперь журнал пишется в UTF-8 и одна
плохая строка не забирает все следующие.

### Тесты

`VetroMediaTests` — добавлены классификация адресов, отказы движка (включая
формулировки curl), окончательный отказ против повтора, расписание backoff,
разбор вывода resolver и защита его входа. Все проходят.

### Что осталось вне этапа

- yt-dlp не входит в поставку: для ссылок на страницы его нужно положить в
  `resolver\` рядом с программой. Проверка на настоящем YouTube без него не
  проводилась — только заглушкой с тем же контрактом.
- Кнопок «Открыть в браузере» и «Копировать адрес» у сообщения о DRM нет: это
  новый элемент в плеере, а его визуал не меняется.
- Живой поток получил в Resource Governor поздние кадры на 25 fps при 180 Гц
  (`late frames`, tier опускался до Constrained). Это поведение этапа 3 на
  необычной частоте, а не сети; разбирать стоит отдельно.

## Этап 8 — AI (сделано)

Цель: субтитры для фильма, у которого их нет, сделанные на этом компьютере, не
мешающие воспроизведению и не выдумывающие текст.

### Среда и модель

- Среда — официальный релиз whisper.cpp 1.9.4 с CUDA 12.4
  (`whisper-cublas-12.4.0-bin-x64`, SHA-256 сверена с опубликованным digest
  GitHub), лежит в `whisper\` рядом с программой и грузится по имени только когда
  AI нужен. Фотография не загружает ничего.
- Модель — large-v3-turbo q5_0 (547 МБ) и Silero VAD 6.2.0 (0.8 МБ). В установку
  не входят: скачиваются по кнопке в меню, проверяются по SHA-256 и удаляются той
  же строкой (27.9). Хранятся в `%LOCALAPPDATA%\VetroLook\models`.
- Звук никуда не уходит (27.12).

### Откуда звук

Не второе декодирование картинки (27.2): второй экземпляр движка без видео, без
вывода, с `ao=pcm` и `untimed`, отдаёт 16 кГц моно. Измерено: 120 с звука за
0.25 с — в 485 раз быстрее реального времени, на любом контейнере и кодеке,
которые плеер и так играет.

### Как идёт работа

`src/transcript.h` — чистые правила, `src/ai.h` — рабочий поток.

- Кусками по 60 с в окне от «чуть позади плейхеда» до +5 минут (27.3). Перемотка
  сдвигает окно; далёкий кусок в работе отменяется; готовое остаётся.
- Последняя реплика куска может быть обрезана его краем — она отбрасывается, и
  следующий кусок начинается с неё: строка слышна целиком и никогда не
  переписывается на экране (27.7).
- Свой VAD решает, есть ли речь: тишина в модель не попадает вовсе (27.5).
- Фильтры (27.6): текст над не-речью с низкой уверенностью, «Субтитры сделал…» и
  прочие титры, выученные моделью из субтитров, строка, повторённая третий раз
  подряд, фраза, зациклившаяся внутри одной реплики.
- Слова хранятся с таймингом с первого дня (27.8).
- Транскрипт сохраняется и открывается готовым; ключ — сигнатура фильма, модель,
  её файл, язык, дорожка и версия настроек декодирования (27.10).
- Экспорт: Shift+A пишет `фильм.<язык>.ai.srt` рядом с фильмом — единственный
  случай, когда программа пишет в папку фильма (27.11).

### Интерфейс

Плеер визуально не менялся. «AI-субтитры» — ещё одна строка в карточке дорожек,
в её же стиле; клавиша A. Сгенерированные реплики показывает тот же Vetro
Bubble, что и обычные. В меню — модель речи (размер · Удалить / Скачать),
язык (Авто / Русский / English) и пропуск тишины.

### Пропуск тишины

Выкл / Мягко / Сильно (28.2), по умолчанию выключен и никогда не включается сам.
Прыгает только через тишину, которую VAD действительно проанализировал:
неизвестное — не тишина, и нечитаемый звук тоже не тишина.

### Что показали измерения

- 60 с звука — 1.3–1.7 с на RTX 3060 Ti, в ~38 раз быстрее реального времени.
  Текст на русском дубляже практически дословный.
- Первая версия считала на процессоре: 651 с CPU и 1.2 ГБ. Причина — ggml грузит
  свой CUDA-бэкенд сам, и тот не находил cuBLAS рядом с собой. Исправлено
  `SetDllDirectoryW` на папку `whisper\`.
- Встроенный VAD whisper.cpp размазывал тайминги: двухсекундная реплика
  становилась двадцатисекундной. Отключён; после этого 99 реплик, самая длинная
  6 с, медиана 1.7 с.
- Сплошная работа кусками давала 17 поздних кадров в минуту и опускала Governor
  до Balanced. Поток теперь ниже обычного приоритета и делает паузы между
  кусками, когда запас больше 30 с: 0 поздних кадров, Governor не сдвинулся.
- Пропуск тишины на записи с пятью паузами по 3.5 с: 6 прыжков, 25.6 с.

Тесты: `VetroTranscriptTests` — 52 проверки (планирование, отбрасывание
обрезанной реплики, фильтры, экспорт, кэш, пропуск тишины).

## Этап 9 — Enhancement + Hardening (сделано) → **V1.1**

### RTX Video Super Resolution

Через фильтр Direct3D 11 video processor самого движка
(`vf=d3d11vpp=scaling-mode=nvidia`) — без SDK NVIDIA и без лицензионного
решения внутри плеера (17.4). Проверено, что закреплённая сборка libmpv
принимает режим и отвергает несуществующий.

Решение — чистая функция `src/enhance.h` (17.2, 17.3):

- Выкл / Авто / Вкл, по умолчанию Авто;
- только RTX, только кадры уже на GPU (`d3d11va`), не для HDR;
- Авто — только при реальном увеличении (≥15 %), от сети, не в маленьком PiP;
- масштаб квантуется четвертями, чтобы перетаскивание окна не пересобирало
  фильтр на каждом кадре;
- если Governor пришлось отобрать улучшение у фильма, оно не возвращается до
  конца этого фильма — иначе нагрузка включала бы и выключала его по кругу;
- сообщение «Улучшение видео временно снижено» — только если пользователь сам
  выбрал «Вкл» (75).

Проверено: 1080p в обычном окне — «не нужно» (увеличение 9 %); развернули на
1440p — включилось ×1.25, загрузка GPU 28 → 36 %, 1 поздний кадр, Governor на
Headroom; вернули окно — выключилось. `VetroEnhanceTests` — 19 проверок.

### Восстановление после сбоя

Пока открыт фильм, раз в 5 с пишется короткая запись: какой фильм и где (32.2,
43); чистый выход её удаляет. Запись, найденная при обычном запуске без файла,
значит, что прошлая сессия закончилась не по воле пользователя, — фильм
возвращается, позицию даёт уже существующая память фильма. Запись используется
один раз: если сбой вызывает сам фильм, он не будет открываться при каждом
запуске.

Проверено: процесс убит на 18:04 → запись осталась → обычный запуск открыл тот
же фильм → после закрытия записи нет.

### Картинка в картинке

- Помнит место и ширину для каждой раскладки мониторов (33.4); на другой
  раскладке открывается в углу по умолчанию.
- Отпущенная рядом с углом — встаёт в угол с тем же отступом; в другом месте
  остаётся где отпустили.
- T — закрепить поверх всех окон или открепить (33.2); помнится вместе с местом.

Проверено: отпущена в 16 px от угла → встала на отступ 24 px; T снял флаг
topmost; выход и повторный вход вернули то же место и откреплённость.
